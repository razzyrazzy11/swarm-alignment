## What dispatch equivalence does and does not mean

The new scheduler aims to remove avoidable implementation overhead while
preserving the registered dispatch rules. Its implementation and tests must
show the same dispatch choices and guards for a fixed completion/event stream,
with unchanged request bodies, model routes, job ordering, concurrency,
reservations, retry rules, cooldown/Retry-After handling, metadata checks and
cutoff. This is a semantics-equivalence claim under a fixed input stream, not a
claim of identical empirical arrival, latency or completion timing. Actual
provider timing can change with wall-clock batch, network and serving state;
the paper must disclose that operational timing limitation.

This admission module neither establishes that scheduler equivalence nor
relaxes a guard on its behalf. The separately registered collector, tests and
operational protocol own it. The scientific estimand, oracle, endpoint,
normalization, host action, budget, bootstrap and scoring are unchanged. No
scheduling change permits a POST retry, condition removal, checkpoint
substitution, budget increase, cutoff relaxation or outcome-directed selection.
